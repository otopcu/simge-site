# SimGe Release Notes

*Last Updated/Edited (DTG): 2026-10-08*

## [0.5.3] - 2026-10-08

### Reliability
- FOM2 reference update: the upper normalized-density anchor is 256 (previously 64), selected after the recorded anchor/slope comparison to reduce score compression in the case-study corpus. The lower anchor 4, slope ln(19), weights and population gate are unchanged. Dashboard defaults, reports, manuscript tables and sensitivity interpretations use the new reference; 256 is not a universal performance threshold.
- **Version Shown Again from Directory.Build.props**: The title bar, About box, start page, generated code and FDD/FED headers showed 0.4.8 after the string resources were regenerated, which dropped the hand-written version lookup. The version now comes from `SimGeAppInfo`, which reads the assembly version set in `Directory.Build.props`, and the stale `AppVersion` resource was removed.
- **FOM2 Federation Evidence**: Added an isolated paper-matched NETN-CBRN TCP experiment with ten federates, five fresh process pairs, separate controlled/operational phases, per-federate manifests and exact send/RTI/receiver correlation checks. Historical telemetry runs remain unchanged. See Architecture 16F.
- **Custom Root Payload in Fora Generation**: Application attributes declared on HLAobjectRoot (for example NETN UniqueId/CreateTime) now survive model, handle, encoder, decoder, entity and specialized generation. RTI control attributes remain separate. The omission was detected by the FOM2 bounded experiment before timing; source FOM definitions and static metrics are unchanged. Fora source changes were not required.
- **Restaurant Sample Inputs**: The Restaurant metrics sample now uses the IEEE 1516-2025 example modules (`RestaurantFOMmodule-2025`, `RestaurantExtensionFOMmodule-2025`, `RestaurantSOMmodule-2025`), with the `EmployeeReference` target path corrected to `HLAobjectRoot.Employee`. The report generator maps its case-study rows to these modules, and its lenient composer now rebinds data-type references after merging, as in the NETN sample. Reports for the replaced modules and previously generated sample source code were removed.
- **Dashboard Analysis Recovery**: Models with duplicate data type names across tables no longer abort the entire dashboard calculation. A Duplicate Type Names card identifies ambiguous definitions; unexpected analysis failures now show an inline message with retry guidance.
- **Command Failure Feedback**: Unexpected errors in Save/Save As, object-model import/export, code generation, and datatype member/Notes dialogs now produce a visible error message. Critical project commands prevent overlapping execution and restore availability after failure or cancellation. Failed or cancelled Notes dialogs leave their parent draft unchanged.

- **FOM1c A3 Reference Re-Frozen**: The NETN metrics report reference of supporting analysis A3 now points at the corrected report, closing the known 0.5.2 release-test exception. A3 was never reported, and the intervening report change was the NETN data-type correction, so the reference was re-frozen rather than archived. The 42-file corpus hash is unchanged and only NETN-LOG shifts band. `SimGe.Model.Tests` now passes with no exception.
- **MOM Integration Crash**: Switching MOM integration on no longer fails with "Collection was modified". The merge runs in the background and raises one structural change per added element; each of those started another collection rebuild over the lists still being written. The editor now refreshes once when the merge finishes, and toggling MOM no longer marks the module as modified.
- **MOM Integration Is Reversible Again**: A module saved while MOM was integrated used to carry the whole MOM tree into its own file as user-defined content, which switching MOM off could no longer remove. Module content is now always written without MOM, and the integration is restored from the module metadata on load, so the editor looks the same while the file stays clean.
### Model Metrics
- **Fom2 Terminology**: Semantic-card and report explanations now distinguish normalized payload density, diagnostic scores, and relative dispersion. High dispersion prompts inspection for potential hotspots; class weights and shares identify the contributors. Population displays use |P_c|, concrete is identified as a sharing-based analysis convention, and payload drill-down names structural byte weights and update-adjusted contributions. Metric formulas, thresholds, and exported CSV field names are unchanged.
- **Fom2 Interpretation Alignment**: High CV is now labeled High dispersion, and reports identify the largest W_i without inferring dominance. Low interaction propensity is described as low normalized payload density; Critical saturation is no longer called Monolithic, and population-gated scores are not labeled Balanced. Joint-view guidance requires class weights and shares before choosing mitigation. Variant labels explicitly compare the lightest/heaviest endpoints rather than claim stability throughout the interval; probability-weighted analysis remains a future extension. The heaviest-path baseline, numeric metrics, and code-generation candidate selection are preserved. Nested variant rows now name the lightest alternative under the lightest policy, rather than selecting its label using heaviest-path weights.
- **Reference Types Weighed by Their Declared Representation**: A reference data type now takes its weight from the representation it declares, as Fom2 defines, instead of from the referenced attribute. A reference to an inherited attribute resolves (it used to fall back to weight 1), as does one naming the reserved `HLAobjectInstanceName`; the MIM's `HLAobjectInstanceReference` now weighs its `HLAobjectInstanceHandle` representation. An unresolved class or attribute no longer drops the weight to 1. A representation that differs from the attribute's data type, or is missing from the model, is listed in the import report. The Restaurant and NETN tables are unchanged at full precision (`EmployeeReference` stays 24 at κ_dyn = 10).
- **Semantics Views: Diagnosis, Payload, Robustness**: The Semantics tab keeps its cards on top and shows one of three views below them, remembered for the session. Diagnosis holds the joint grid and propensity curves; Payload holds concentration, drill-down, and structure × payload; Robustness shows how far the results move under the calibration profiles and the variant choice, with collapsible calibration and variant tables. The calibration table moved out of the gear panel.
- **Variant Choice Bound**: Variant records are still weighed by their heaviest alternative (Fom2 Eq. 6); SimGe now also computes the lightest-path bound, model-only and without usage probabilities. The Robustness view shows the resulting SSI_n range and zone per domain, the share of weight that depends on the variant choice, and every variant record reached by the payload with its lightest and heaviest alternatives. Payload bars can be split by variant choice, and cards distinguish sampled calibration results from the two variant endpoints.
- **Object Model Analysis Workspace**: **Analyze object models** on the Start Page, or **View → Project Workspace → Object Model Analysis**, analyzes every FOM module through the dashboard path. A provenance line records input SHA-256 hashes, calibration, composition policy, and version; the module table and the collapsible per-module sensitivity section (κ_dyn sweep, ΔΨ, E values, all 22 profiles in readable groups) copy as Markdown, CSV, LaTeX, or pgfplots data. Modules are listed by short name. For the corrected samples, tests reproduce the Fom2 case-study values and selected sensitivity results now detailed in Supplement B. The dashboard Ψ chart now exports as PNG.
- **Readable Axes and Origins**: Large values on the Ψ chart and the depth × W_i scatter are printed as whole numbers instead of `1.02E+03`; Pareto weights use thousands separators; member origins name the short module (for example `RPR-Base_v3.0`) instead of the full FOM title.
- **User Manual Screenshots**: The Dashboard, Model Metrics & Reports, and Start Page pages now walk through the semantic cards, joint diagnosis, propensity ranges, calibration sensitivity, drill-down, structure × payload, module card badges, dependencies and composition, and Object Model Analysis with NETN sample screenshots rendered from the production views.
- **Joint Saturation × Dispersion View**: A Semantics grid crosses the Ψ zone of SSI_n with the CV_p band for both domains and restates the paper's zone and dispersion responses. Gated domains appear in a separate column; unavailable metrics are described, not placed.
- **Calibration Sensitivity in the Dashboard**: The 22 Fom2 calibration profiles (κ_dyn and λ perturbations, anchors fixed) are recomputed in the background. Cards state zone or band stability, the Ψ chart shades each domain's SSI_n range, and the gear panel lists a κ_dyn sweep. The anchor sliders are relabelled as an interpretation preview.
- **Payload Drill-Down**: Pareto bars can be split by source module, update type, or κ_dyn dependence; clicking a class lists its members with origin, w(T) × λ, and contribution.
- **Structure and Payload Lenses**: A depth × W_i scatter and an Overview strip place hierarchy shape beside carried payload.
- **Resolution on the Module Card**: The provenance strip above the module card is gone. The card shows one green badge when the composed analysis resolves cleanly, or one badge per issue (lenient composition, unresolved references, missing or out-of-scope dependencies); unresolved references open Quality, the others open Dependencies and composition. The Semantics view still warns when payload may be understated.
- **Module Details**: Details now shows the content file's SHA-256 (the value Object Model Analysis records, with copy), a copy button for the module ID, whether the MOM is integrated, and the security classification, application domain, and copyright when present. The Dirty row is replaced by an **Unsaved changes** badge on the module card.
- **Dependencies and Composition**: The Dependencies section now lists every module of the analysis in composition order, marks direct and transitive dependencies (with the module that brings each transitive one in), and shows missing dependencies with Import where possible. Double-click a module to open its editor. It replaces the separate included-modules text and the "Analyzed as merged with" box. A dependency declared by the module stays direct even when another dependency also reaches it, and changing the declared dependencies re-runs the analysis.
- **One Card Color System**: All dashboard cards now separate category, status, and selection. The left strip and value color show the assessment (green Balanced/Homogeneous, yellow Transitional/Moderate, orange High, red Critical/error, grey withheld; descriptive values have no strip); a category icon badge sits beside each label, and selection is blue. Balanced cards no longer look like warnings. CV_p cards show their dispersion band, largest W_i class and share, and P_c; a single class reads `Single class`, not Homogeneous. Badges read `High anemia` and `Balanced · saturation only`, and `Ψ < 0.001` replaces `Ψ = < 0.001`.
- **No God Class Verdict from Dispersion**: The `CV_p >= 1.0` zone is now `High dispersion` instead of a God Class verdict, matching Fom2: dispersion marks uneven weights but does not identify a class or establish the design smell. Existing sample reports keep the old label until regenerated.
- **Collapsible Payload Concentration**: OC and IC payload summaries and Pareto charts now open independently on demand; both sections start collapsed.
- **Semantic Curve Legend**: Matched the paper's centered subscript legend and curve styles: blue solid anemia (OC only), red dashed saturation (OC and IC). Calibration previews use lighter dotted lines to remain distinct.
- **Semantic Curve Annotations**: Added paper-aligned x_low/x_high anchor labels, Ψ = 0.50 crossings, critical-point coordinates, and an OC-only Balanced-range arrow. Reference annotations stay fixed during previews, with explicit pre-gate and zero-value explanations.
- **Dynamic Cardinality Display**: Replaced the inactive k_dyn preview slider with a read-only reference value of 10. Only anchors and log slope alter curve previews; changing cardinality requires a new model analysis. The Dashboard user guide now documents the semantic cards, curves, Pareto charts, health strip, and these calibration limits.
- **Semantic Curves and Payload Contributors**: Replaced the SSI color band with reference anemia/saturation curves and domain-specific OC/IC markers, fixing the red-band/Balanced-IC contradiction. Calibration is a pale dotted preview; cards and reference markers remain consistent. Added per-domain top-five payload bars, cumulative shares, and an Others aggregate using the complete concrete population.
- **Visible Analysis Provenance**: A top strip now reports actual strict/lenient composition, included modules, unresolved type references, and missing declared dependencies, including transitive ones. Module Only and dependencies omitted from scope are explicit. The merge-conflict banner now correctly identifies lenient results.
- **Semantic Diagnosis in Existing Cards**: Each existing SSI_n card now shows Ψ, a colored Balanced/Transitional/High/Critical badge, its driving component, and concrete population P_c. Small populations show Gated with an informational raw-value note; empty or undefined domains show Unavailable. SSI and payload-dispersion warnings are independent. The shared card template retains its information, copy, and navigation behavior. Cards use the same reference calibration as reports; sliders add pale dotted curve previews.
- **Semantic Calibration Profiles**: Added immutable analysis profiles for dynamic-array cardinality and Conditional/Periodic weights, while preserving existing default calls. The FOM2 sensitivity sample recomputes recursive weights across 22 profiles and exports propensity drift, raw metrics, and publication figures. Default results match the 17 archived Restaurant/NETN configurations; 122 relevant tests pass.
- **Semantic Saturation Propensity (`Psi_SSI`)**: The anemia and saturation sigmoids now act on the log2 ratio of `SSI_n` to its anchor, with slope `a = ln 19`, replacing the linear form with `k = 0.15`. Each component is 0.5 at its anchor and 0.95 one doubling beyond it (`SSI_n = 2` and `512`); previously saturation reached 0.95 at about 83.6 and anemia could not exceed about 0.646. At `SSI_n = 0` anemia is 1; an undefined `SSI_n` (`mu_D <= 0`) is suppressed instead of scored as anemia. Reported `Psi_SSI` values and zones change accordingly.
- **Shared SSI Gauge Math**: The dashboard SSI gauge now calls the same `MetricAnalysisCore` functions as the reported scores, so markers, tooltips, and cards agree at default settings. The calibration slider "Sigmoid k" is replaced by "Log slope a" (1–6, default 2.94).
- **Undefined Payload Dispersion**: `CV_p` is undefined for an empty population or a zero mean payload. The synthesis layer now reports these cases as `Not Available` instead of `Homogeneous`, and the dashboard shows `N/A`. The hotspot threshold is now `CV_p >= 1.0` everywhere (previously `> 1.0` in synthesis, findings, and dashboard warnings).

### Object Model
- **Reference Datatype Targets Preserved**: A reference datatype whose `referenceClass` or `referencedAttribute` cannot be resolved on import (for example `HLAobjectClass.Employee` in the IEEE 1516-2025 Restaurant SOM, where the class path is `HLAobjectRoot.Employee`) no longer loses both names on export; they are kept as written. The import report lists such targets in a new Unresolved Reference Datatype Targets section. Selecting a class in the reference datatype editor replaces the kept name.
- **Basic Representation Endian and OMT Export**: A basic data representation that declares no endian (optional in DIF and FDD, as for `UnsignedShort` in the IEEE 1516-2025 Restaurant FOM) is no longer given `Big` on import. The table shows `(not declared)`, the editor leaves the endian unselected with a short note, and DIF/FDD export omits the element. OMT export now writes every element the OMT schema requires: `size`, `interpretation`, `endian`, and `encoding`. An empty interpretation or encoding is written as an empty element, and an undeclared endian as `Big`, because the OMT schema accepts only `Big` or `Little`.
- **Unresolved Data Type References in the Import Report**: Schema validation does not check whether a datatype name refers to a defined datatype, so such errors previously passed import silently. After MIM binding, the import report now lists every datatype reference that did not bind, in an Unresolved Data Type References section. A name that exists as another datatype kind is reported as a kind mismatch, for example `Preparation.representation -> HLAboolean: an enumerated datatype, not a basic data representation` in the IEEE 1516-2025 Restaurant FOM. Names defined in a module that is not loaded yet are marked as resolving later.
- **Class and Property Draft Validation**: Missing/unresolved datatypes, Transportation, IC Order, and Directed Interaction targets now produce saveable Warnings; invalid supplied enum values remain Errors. Added Attribute NA/update-condition checks and declared-member diagnostics in class dialogs. Directed Interactions accept Neither and resolve targets case-sensitively. Missing datatype and target names survive Save/reopen.
- **Properties in New Classes**: Attributes and Parameters can now be added before their Object/Interaction Class is saved. Nested editors retain the exact draft owner, show a placeholder for an unnamed class, and avoid binding to a same-named live class. Cancelling the new class leaves no class or property in the project.
- **Editor Errors and Warnings**: Added shared validation results and a common validation/Save lifecycle for all 23 OME editor dialogs, including Enumerator, Record Field, Alternative, and POC. Missing or unresolved Representation now shows a Warning while allowing draft saves; name/member errors and known floating representations block Save. Every dialog rechecks Errors before committing; OC/IC Name errors now also block Save. Other existing rule severities are retained. Rejected insertions keep the dialog open, and all dialog exit paths release subscriptions.
- **Shared Datatype Name Validation**: All seven datatype/basic-representation tables now share one case-sensitive naming scope. Create and edit dialogs reject cross-table conflicts, exclude the edited original, and recheck names before applying changes. Older conflicting models remain loadable for diagnosis and repair.
- **Consistent HLA Names**: Common XML/HLA name validation now accepts valid Unicode identifiers. Variant Record alternatives use the same case-sensitive name checks in member and parent dialogs, including reserved `NA`. Datatype reference selections preserve exact name case. Name errors identify the offending character and position, explain the correction, and retain the applicable standard clause as supporting information in tooltips and copied messages.
- **Enumerator Value Format**: Fixed acceptance of malformed values such as `4,2.5//`. Enum editors require comma-separated decimal integers, check standard representation bounds, and revalidate existing values when Representation changes.
- **Datatype Member Editors and Validation**: Enumerators and Fixed Record fields now use Add/Edit dialogs with validated names, case-sensitive duplicate checks, and isolated drafts. Values cannot belong to different enumerators. Array cardinality now checks counts (including zero), dimension lists, ranges, and Dynamic. Cancelling the datatype discards staged member and note edits.
- **Class and Property Names**: A child Object Class and an Attribute may now share a name under the same parent; the same applies to Interaction Classes and Parameters. Creation, renaming, and reparenting use separate class/property naming scopes, consistent with IEEE 1516.2-2025. Standalone and nested property editors now reject inherited-name conflicts, including conflicts introduced in descendants by superclass edits or class moves. Comparisons respect case; the selected destination is used when moving an item.

### Code Generator
- **Fora 2025 Callback Compatibility**: Generated federates implement the IEEE 1516.1-2025 callback signatures from Fora commit `660ee9b`; transportation metadata uses `TransportationTypeHandle`. The callback loop now selects `CallbackModel.Evoked`, including the checked-in NETN sample managers, and the bundled API snapshot is refreshed. Requires Fora `20260720.1.0` at commit `660ee9b` or a later compatible build. Additional callback metadata is accepted but not yet exposed through application hooks.
- **Federations from Several FOM Modules**: Generated Fora code creates the federation from the FAME federation's FOM modules and their dependencies, in load order, with the chosen MIM and logical time (IEEE 1516.1-2025 §4.5), and joins with the application's join modules (§4.11). Modules are read from a `Fom/` folder and sent with their content, so the RTI host needs no copy. Only an already existing federation is ignored at creation; other rejections reach the caller instead of being swallowed.
- **FOM Files Written with the Code**: Code generation writes each module to `Fom/`, copied from the imported XML where available, plus the composed FOM as one FDD (1516-2025 for Fora, 1516-2010 otherwise) and one HLA 1.3 FED, into every generated application's folder. This replaces the export of the first FOM module alone, which also added the HLA 1.3 MOM to that module in the project. Missing dependencies and conflicts are reported as `CG1030` warnings.
- **Fora API Snapshot**: The bundled `Fora.Client` contract snapshot was refreshed for `FomModuleSource` and the new create/join overloads; contract validation now covers 37 service calls.
- **Object Instance Registration Audit (IEEE 1516.1-2025 §6.2 – §6.8)**: Audited all Fora generators, call catalogs, templates, and sample applications against Fora commit `887aa40` (object instance name reservations). Verified that SimGe generates exclusively the unnamed registration overload `RegisterObjectInstanceAsync(ObjectClassHandle, CancellationToken)`, relying on RTI unique name assignment per §6.8. SimGe emits no named registrations (`RegisterObjectInstanceAsync(..., string ...)`), eliminating dependencies on unreserved instance names and preventing `HlaObjectInstanceNameNotReserved` exceptions. Verified that the four ambassador reservation callbacks (`ObjectInstanceNameReservationSucceededAsync`, `ObjectInstanceNameReservationFailedAsync`, `MultipleObjectInstanceNameReservationSucceededAsync`, `MultipleObjectInstanceNameReservationFailedAsync`) are generated as base stubs in `ClassCodeGen_FdGen_Fora`. Documented in Architecture 11C §5.1.1.

- **Object Instance Registry in Generated Code**: The SOM's Object Instance Registry now drives the generated Fora federate. Names are reserved while the federate starts (`ReserveObjectInstanceNameAsync`, or `ReserveMultipleObjectInstanceNamesAsync` for a pattern) and the generated manager waits for the RTI's answer by evoking callbacks itself, because `CallbackModel.Evoked` delivers it only inside an evoke call (IEEE 1516.1-2025 §6.3, §6.6). An instance is registered with its name only after the reservation succeeded (§6.8.3 f); a refused reservation fails the run with `InstanceNameReservationException`. Startup declarations register when the federation is ready, advisory-driven ones from the heartbeat after the Start Registration advisory (§5.14; the federate keeps the advice per class and clears it when the relevance switch is disabled), and on-demand ones through `Register<Class>InstancesAsync`. A name is released when its instance is deleted and the declaration asks for it (§6.4). `DeclaredInstances` reports the state of every declaration; the generated README lists them. Models without declarations generate exactly the code they did before.
- **Initial Attribute Values**: A declaration can give attributes of its class a starting value, checked against the attribute's data type while it is typed (booleans, integers by range, floats, characters, strings, enumerators by name or value, hexadecimal byte arrays; records, variants and other arrays are not supported yet) and by the generator (`CG5010`, `CG5011`). The generated manager passes the values to the class's register method, which sends them with the first update right after the instance is registered. A deleted attribute leaves the grid and the declaration; a rename keeps the value; choosing another class starts without values. A declaration can send them right after registration (default) or only when requested; either way the generated manager answers Provide Attribute Value Update for declared classes from the state of the entity in one update, so a federate that joins later receives them (checked against a Fora RTI). A declared instance registered without values no longer sends an empty update. Enumerations and booleans are chosen from a list.
- **Region / DDM Scope for Declared Instances**: A declaration whose class has dimensions can give each dimension a range `[lower, upper)` in a new **Region / DDM Scope** section of the card (the dimension's upper bound is shown, and the range is checked against it). The generated manager then registers the instances with `RegisterObjectInstanceWithRegionsAsync`: it creates and commits the region once, associates it with every attribute the instances publish, and deletes it in the cleanup. Without a range, or for a class without dimensions, the instances are registered in the default region, which the generator reports for a class that has dimensions (`CG5012`); an invalid range stops generation (`CG5013`). Ranges are saved in the `.sfom` with the declaration and follow the dimensions by name. The new calls are in the Fora contract catalog and in the snapshot (checked against a Fora RTI with the Chat sample's `Group` dimension).
- **Instance Declaration Validation**: The pre-generation gate reports `CG5001`–`CG5009`: a missing class, a name beginning with "HLA" (§6.2.3 d, §6.5.3 d; case-sensitive, so `hla` is legal), an empty name or invalid pattern, a name two declarations both reserve, an advisory-driven declaration without the Object Class Relevance Advisory switch, and declarations skipped because the class is unpublished or pruned. The registry's HLA-prefix check in the OME is now case-sensitive like the standard.
- **Fora Save, Restore, Ownership and Time Callbacks**: The generated federate base declares the IEEE 1516.1-2025 forms of Federation Not Saved (with `SaveFailureReason`), Federation Save / Restore Status Response, Initiate Federate Save with a time, Report Federation Execution Does Not Exist, Inform Attribute Ownership, Attribute Is Not Owned, Attribute Is Owned By RTI, Flush Queue Grant (with the optimistic time) and Request Retraction. Generated federates compile against the current Fora source again. The bundled `Fora.Client` API snapshot was refreshed from a Release build of the same Fora tree, so the contract validator and the generator now see the same members.
- **Provide Attribute Value Update for Every Published Class**: The generated simulation manager answers Provide Attribute Value Update (IEEE 1516.1-2025 §6.22) for the owned instances of every class the federate publishes, not only those the Object Instance Registry declares: one update with the requested attributes that have a value, carrying the SOM's update tag when it declares one. A federate that joins later receives the current values without application code. `ProvideOwnedAttributeValuesAsync` is virtual, so an application can answer a class differently and call the base for the others. Applications that wired `AttributeValueUpdateRequested` to their own answer can drop it.

### Workspace UI
- **Start Page Shows Project Health and a Next Step**: The Start Page now shows the project's standard, counts, folder chips, and save state, four status tiles (Modules, Dependencies, Analysis, Generated code), a **Next step** card that suggests one action for the project's state, a **Workflow** panel with each stage's status, **Recent projects** (switching asks about unsaved changes), and a **Learn** card. The metadata panels are folded into the header, and the dependency graph is unchanged. See the Start Page chapter of the user manual.
- **Object Instance Registry**: SOM modules have a registry of the object instances their federate registers, in a last OME tab and in an `Instances` tab of the Object Class editor. Declarations choose a class, a naming strategy (RTI-assigned, one reserved name, or an indexed pattern) and a trigger (startup, Start Registration advisory, on demand), are validated as they are edited (including the "HLA" name prefix), and are saved in the module's `.sfom` metadata. The view follows the other split views: detail on the left with the Add / Duplicate / Delete toolbar, list on the right with a toolbar for Copy Table (Markdown), grouping by class, strategy or trigger, and the filters. A reserved name has a Lifecycle Policy (release when the instance is deleted, or keep reserved). Groups use the Dashboard's round chevron expander and the master toolbar is a single row. Cancelling the Object Class editor reverts its instance edits. See the [Object Instance Registry](UserManual/ObjectInstanceRegistry.md) chapter.

### Reports and Analysis
- **Data-Type Impact Analysis**: Added `TypeImpactAnalyzer` (`SimGe.Model.Analysis.Impact`), which inverts the OMT data-type reference graph to answer "what breaks or shifts if I change this type?". It computes one transitive closure for two change kinds — **Removal/rename** (every referrer loses its binding and blocks code generation) and **wire-format shift** (a representation/encoding change forces every embedding codec to be regenerated and re-coordinated across federates) — and reports the affected attributes, parameters, record fields, variant discriminants/alternatives, classes, and (with an owner→module map) dependent modules. A new **Data-Type Impact** section in the module analysis report ranks declared types by blast radius. Covered by unit tests.
- **Impact Report Dependent-Modules Column**: The Data-Type Impact section of composed sample metric reports (NETN / RPR / Restaurant) now attributes each affected element to its owning module, so the **Dependent Modules** column shows which modules a data-type change would reach across the composition. Attribution is built from the pre-merge module set via `TypeImpactAnalyzer.BuildOwnerModuleMap`; single-module reports omit the column.
- **Data-Type Delete Impact Warning**: Deleting a data type now runs the impact analysis inside the delete-confirmation dialog. Instead of a generic "are you sure?" prompt, it reports how many references across how many classes will break (falling back to unresolved type names and blocking code generation) and lists a sample of the affected attributes/parameters/fields, so the deletion can be confirmed or cancelled with full knowledge. The user may still proceed.
- **Data-Type Rename Impact Preview**: Renaming a data type that other elements reference now shows a confirmation first: in-module references follow the rename automatically, but cross-module references by the old name and generated code do not, so the user can proceed or cancel with that in view. No prompt when nothing references the type.
- **Show Impact / Usages (Project Explorer)**: Right-clicking a data type in the Project Explorer opens an on-demand impact/usages report — which elements reference it, how a removal/rename would break them, and what a representation/encoding change would force to be regenerated and re-coordinated across federates. It uses the same analysis engine as the delete-time warning; the action is enabled only for data-type nodes.
- **Non-Blocking Report Generation**: OMT report generation now runs off the UI thread. `CReportVM.RefreshReport()` previously started a worker thread and immediately `Join()`ed it, then rendered the RDLC on the UI thread, freezing the app for large FOMs (e.g. NETN-CBRN).
